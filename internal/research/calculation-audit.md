### Точный план и приблизительный эскиз

- `ht` сначала требует минимум 3 вершины, все длины и соблюдение неравенства многоугольника: одна сторона не должна быть практически равна сумме остальных или превышать её (`pt`, `ht`, 464–471, 546–552).
- Для прямоугольных направлений без расхождения больше 0,5 см строится план `orthogonal`; самопересечение проверяется (`ct`, 365–370).
- Произвольный контур при наличии требуемых диагоналей триангулируется. Итерационный расчёт подгоняет длины и проверяет самопересечение, знак углов и соответствие эскизу (`dt`, 399–442). Это не универсальный доказанный геометрический решатель.
- Если точному расчёту недостаёт диагоналей, `gt` пробует приблизительный план `sketch`, сохраняющий заданные длины и близкие эскизу углы (`mt`, `gt`, 472–565). В интерфейсе для него площадь и цена обозначаются приблизительными.
- На исполненных примерах Г-образный план 400 × 400 см с вырезом 200 × 200 см дал `orthogonal`, 12 м² и 16 м. Трапеция с нижней стороной 400 см, верхней 350 см и высотой 300 см без диагонали дала `sketch`, 11,25 м² и 13,54 м; с диагональю 460,98 см — `triangulated` с теми же результатами.

## Полотно и доплаты

Обозначения: `round2(x) = Math.round(x × 100) / 100`; все цены — рубли.

| Что считается | Восстановленное правило | Источник |
| --- | --- | --- |
| Допустимое сочетание полотна | Поиск записи `canvases` для способа монтажа, цвета и фактуры; отсутствующее сочетание не даёт строки полотна | `ae`, `F`, `ce`, 112; `je`, 151–158 |
| Доступный способ монтажа | Короткий габарит ограничивается `maxWidthCm`: hot 630, soft 600, cold 400; в проверке короткий размер сначала округляется до целого сантиметра | `se`, 112; `Ku`, 3561–3568; API `stretches` |
| Тариф ширины | Первая ширина рулона `widthM >= shortSpanM`; если такой нет — последняя, самая широкая запись | `ue`, `le`, 112; `je`, 154 |
| Оплачиваемая площадь `B` | `max(фактическая площадь, billedAreaSqm либо фактическая площадь)` | `je`, 154 |
| Малая площадь | При **B < 5 м²** ставка = `smallRatePerSqm` записи полотна либо `baseRatePerSqm` монтажа. В сохранённом прайсе это 550/600/650 ₽ для hot/soft/cold. При B = 5 действует обычная ставка ширины | `je`, 154; API `smallAreaSqm`, `stretches` |
| Минимальная цена полотна | Минимум из записи `canvases.minCanvasRub`, иначе минимум способа монтажа. Цена строки = `Math.round(max(B × ставка, минимум))` | `je`, 154–157 |
| Гарпун | Добавляется отдельной строкой по фактическому периметру, стоимость 0 ₽, если у монтажа указан текст `harpoon` | `je`, 157 |
| Усадка | По монтажу: hot 8%, soft/cold 4%, если в прайсе не задано своё значение. Пользовательская настройка ограничена диапазоном 0–20% | `v`, 12–15; `af`, 3883–3894 |
| Нужен ли шов | `shortSpanM × (1 − shrinkPct / 100) > максимальная ширина рулона + 1e-9`. Шов не оценивается отдельной ценой этим кодом | `je`, 155 |
| Дополнительные углы | `max(0, число вершин − freeCount)` × ставка. В API freeCount = 4, ставка 50 ₽ | `je`, 159–162; API `extras` |
| Прочие доплаты | Для `basis: piece` = `max(0, floor(selection.extras[id])) × ставка` | `je`, 159–162 |

Для холодного монтажа в сохранённой матрице есть только белый матовый вариант. Полупрозрачная фактура присутствует в общем списке, но не имеет записи в `canvases` и поэтому не становится доступным сочетанием.

Усадка **не уменьшает оплачиваемую площадь** и **не участвует в выборе тарифной ширины рулона**. Она влияет на признак шва. Например, короткая сторона 3,4 м требует тарифа рулона 3,6 м, хотя с усадкой 8% она меньше 3,2 м. Это наблюдаемая особенность, которую надо подтвердить у заказчика перед переносом.

Доплаты за кривую и вырез присутствуют в прайсе и расчётной функции, однако в изученной форме комплектующих для них не обнаружены отдельные управляющие поля; при восстановлении сохранённого проекта `extras` очищается (3719). Наличие функции не доказывает доступность такой опции покупателю.

## Комплектующие и округление

`je` (163–187) рассчитывает только выбранные позиции. В текущем API нет автоматического обязательного добавления полного набора крепежа.

| Тип выбора | Источник количества |
| --- | --- |
| `select: many` | Пользовательское `selection.counts[itemId]`, независимо от `basis` группы |
| `select: one`, `basis: perimeter` | Вручную введённая положительная длина группы, иначе периметр комнаты |
| `select: one`, `basis: length` | Введённая длина группы; без неё позиция не рассчитывается |
| Штучные позиции и дополнения | Пользовательское количество; дополнения обрабатываются как отдельная группа с множественным выбором |

Обычное количество округляется формулой `ceil(round2(количество) / шаг) × шаг`, где **шаг = `item.packOf`, иначе `group.roundUpTo`**. При нулевом шаге остаётся `round2(количество)`. Стоимость строки комплектующей округляется до целого рубля. Ввод через счётчик `Yd` дополнительно округляет введённую величину вверх до целого (3827–3834).

`stickLengthsM` и выбранное `sticks[itemId]` влияют на текст строки, но в `je` не заменяют шаг из `packOf/roundUpTo` (179–180). Для будущих позиций с несколькими длинами палок это следует проверить отдельно.

После нормализации сохранённого API доступны 6 групп: крепёж периметра (`many`, 35 позиций), световая линия (`many`, 18), скрытый карниз (`one`, 4), крепёж спотов/люстр (`many`, 25), обход труб (`many`, 6), базовый комплект (`many`, 9). Группы с `hidden: true` исключаются целиком (`te`, 90–98). В частности, актуальный профиль — **множественный выбор с ручным количеством**, поэтому старая формула «профиль всегда автоматически по периметру» для этой конфигурации неверна.

### Карниз

Для `one + length + pieceMaxM` функция `De` (139–144) переводит длины в целые сантиметры, определяет `число частей = ceil(длина / максимум части)`, затем округляет длину каждой равной части вверх до шага группы, ограничивая максимумом части. Итоговый метраж = число частей × длина части.

В актуальном прайсе максимум части 2 м, шаг 0,1 м. Ввод **4,95 м → 3 × 1,7 м = 5,1 м**. Белый карниз ПВХ стоит 700 ₽/м → строка **3 570 ₽**. API v150 не содержит `joint` у группы карнизов, поэтому автоматические соединения **не добавляются**. В резервном v8 `joint` есть; код способен добавить `число стыков × joint.packOf` соединителей, но это не поведение сохранённой актуальной конфигурации.

Код поддерживает также размерные товары: ближайший больший размер/тарифная ступень либо шаг размера, предупреждение о неуказанном размере (`be`, `xe`, 121–128; `Xd`, 3835–3843). Найденные размерные кронштейны расположены в скрытой группе, поэтому их наличие в данных не подтверждает доступность в текущем интерфейсе.

## Общая сумма проекта

`sd` (3612–3618) объединяет комнаты. Минимум заказа, доставка и обработка применяются **один раз ко всему проекту** через `Me` (190–194).

1. `G` — сумма всех строк товаров всех комнат. При G = 0 итог и доставка равны 0.
2. Доплата до минимального заказа `M = max(0, 2500 − G)`.
3. Посылки определяются по группам строк с положительной стоимостью. Обычные строки образуют одну общую посылку. Каждая выбранная отдельная группа образует ещё одну посылку; повторение группы в другой комнате не добавляет новую. API указывает `cornice`, `group-1`, `profile`, `line-30`; скрытый `group-1` обычно не участвует. `separateEach` отсутствует, нормализатор задаёт `true`.
4. Доставка `D = число посылок × 300`.
5. Предварительный итог `T = ceil(round((G + M + D) × (100 + 3)) / 100)`.
6. Если посылок больше одной, T увеличивается по 1 ₽, пока `T × 100` не делится на число посылок без остатка. Для трёх посылок это может добавить до 2 ₽.
7. Показываемая обработка = `T − G − M − D`. Поэтому она может слегка превышать ровные 3% из-за округления и делимости на посылки.

## Состояние комплекта и ограничения вывода

При изменении периметра более чем на 0,5 м либо количества углов `ld` очищает выбранную комплектацию целиком и показывает сообщение о сбросе (3622–3628). Изменения в пределах 0,5 м и при прежнем количестве углов её сохраняют. Сброс связан с геометрией, а не полноценной проверкой совместимости материалов.

В клиентской части подтверждён фильтр сочетаний полотна и ограничения способов монтажа. Матрица совместимости всех комплектующих, складские остатки, производственный раскрой и серверная проверка цены из этого архива не восстановлены. Фронтенд отправляет проект на сохранение и ожидает от сервера адрес страницы расчёта; интерфейс обещает дальнейшую оплату в Ozon. Само создание расчёта, фиксацию цены, фактическую оплату и обработку на сервере по архиву проверить нельзя.

Для нового ТЗ можно использовать найденные поля и правила как материал для сверки. Отдельно требуется утвердить наследование малых тарифов, оплачиваемой площади охватывающего прямоугольника, округлений и минимального заказа. Посылки и Ozon описывают прототип; в первый этап нового проекта они не переносятся. Пользователь повторно подтвердил сценарий предварительной сметы и заявки менеджеру без оплаты через Ozon.
